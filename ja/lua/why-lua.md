# Wippy が Lua を採用する理由

Wippy が主要なランタイム言語として Lua を採用しているのは、プラットフォームが求めるプロセス分離と組み込みの要件に適しているためです。このページでは、その設計上の選択とトレードオフを説明します。プログラミング言語全般の優劣を論じるものではありません。

これは実行可能なチュートリアルではなく、概念的な設計ノートです。ランタイムの性質を説明し、具体的な API を定義するリファレンスページを案内します。

## ランタイムの要件

Wippy はユーザー定義ロジックを分離されたプロセス内で実行します。各プロセスは独自のメモリを持ち、ランタイムが公開した機能だけを受け取ります。多数のプロセスを同時に実行できるよう、組み込み言語には次の性質が必要です。

- **プロセスあたりのオーバーヘッドが小さいこと。** プロセス数が増えても、メモリ使用量を実用的な範囲に保つ必要があります。
- **ケイパビリティの分離。** ランタイムが、各プロセスで利用可能なモジュール、関数、システム操作を制御できる必要があります。
- **インプロセスでの組み込み。** Wippy の Go コアが、プロセスごとに言語環境を作成、設定、停止できる必要があります。
- **制御されたモジュール読み込み。** モジュールは任意のファイルシステムパスではなく、ランタイムの許可リストまたは宣言されたレジストリインポートから取得する必要があります。
- **小さな言語表層。** アプリケーションコードは読みやすく、生成、レビュー、lint が容易である必要があります。

## 検討した選択肢

### Python

Python には大規模なアプリケーションおよびデータ処理のエコシステムがありますが、そのインタープリター、インポートモデル、パッケージに関する前提は、Wippy のプロセス単位の組み込みおよびケイパビリティモデルとは一致しません。Python サービスは、明示的なサービス境界を介して Wippy と統合できます。

### JavaScript

JavaScript ランタイムには複数の組み込み方法があります。ただし、そのモジュールおよびパッケージのエコシステムには、Wippy が使用するレジストリスコープの読み込みモデルを提供するための別の統合層が必要です。Wippy はアプリケーションコード向けに、ホストが制御できる表層がより小さい Lua ランタイムを選択しました。

### Go

Go は Wippy のコアランタイムに使用されています。コンパイル済みの Go コードやプラグインでは、ユーザー定義のアプリケーションロジックに必要な、分離されたプロセス単位の組み込み環境を同じ形では提供できません。

### WebAssembly

WebAssembly は、主要な記述言語である Lua を置き換えるのではなく、相補的な役割を担います。両者の役割分担については、[Lua と WebAssembly](#lua-と-webassembly)で説明します。

## Lua が適している理由

### ホストが制御する組み込み

Lua はホストアプリケーション内で動作するよう設計されています。Wippy はプロセスごとに環境を作成し、スケジューラーとレジストリに接続して、グローバルおよびモジュールローダーを制御します。`require` が読み込むのは、その環境にすでに導入されているモジュールだけです。常に利用できる基本モジュールと標準ライブラリ、実行可能エントリにアンビエントに提供される `process` モジュール、`modules:` で許可された組み込みランタイムモジュール、`imports:` で宣言されたレジストリライブラリが対象です。ファイルシステムパスを検索したり、ネットワークからパッケージをインストールしたりはしません。そのため、アプリケーション側に読み込み規則を実装しなくても、エントリごとに異なるモジュールセットを与えられます。

### 言語表層

Lua は簡潔な構文と小さな標準環境を持ちます。Wippy は型注釈と lint を追加し、基礎となる実行モデルを変えずにコードを段階的に検査できるようにしています。

### 協調スケジューリング

Lua のコルーチンは Wippy の協調スケジューリングモデルに対応します。プロセスはチャネル操作や I/O 操作の間に yield でき、その間スケジューラーは別の処理を実行できます。

## トレードオフ

Lua には、pip や npm に相当するインプロセスのパッケージエコシステムはありません。Wippy はネットワークからパッケージをインストールする代わりに、組み込みランタイムモジュールを許可リスト経由で、アプリケーションライブラリをレジストリインポート経由で提供します。大規模な外部ライブラリに依存するワークロードは、サービスまたは WebAssembly コンポーネントとして実行できます。

また、他の言語から移行する開発者にとって Lua はなじみが薄い場合があります。構文は簡潔ですが、本番コードにはチーム内の規約、レビュー、lint が引き続き必要です。

## Lua と WebAssembly

Wippy は相補的な 2 つのランタイムを提供します。

- **Lua** は、アプリケーションロジック、ツール、エージェントの主要ランタイムです。
- **WebAssembly** は、コンパイル済みのワークロードや WASM をターゲットにできる既存コードを実行します。

Lua と WASM のプロセスエントリは Wippy のプロセスモデルを使用し、Lua と WASM の関数は登録済み関数エントリとして公開されます。どちらの統合もレジストリとランタイムセキュリティポリシーを通じて設定します。Lua コードから登録済み WASM 関数を呼び出すことができ、WASM プロセスから登録済み Lua 関数を呼び出すこともできます。
