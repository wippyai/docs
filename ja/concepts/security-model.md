# セキュリティモデル

Wippy は実行分離と属性ベースアクセス制御（ABAC）を組み合わせています。分離は、コードが到達できるモジュールとホストリソースを決定します。ABAC は、現在のアクターとポリシースコープで保護対象の操作を許可するかを決定します。どちらの境界も重要です。モジュールをインポートしてもその権限は付与されず、ポリシーによって未宣言のモジュールを Lua コードから利用可能にすることもできません。

## 認可規則

セキュリティコンテキストは **アクター** と **スコープ** を保持できます。アクターは主体を識別し、メタデータを含むことがあります。スコープは変更不能なポリシーの集合です。ポリシーはアクションとリソースにマッチし、アクターまたはリソースのメタデータを調べて、`allow`、`deny`、`undefined` のいずれかを返します。

アクターとスコープの両方が存在する場合：

1. マッチする deny が 1 つでもあれば、deny が優先されます。
2. allow が少なくとも 1 つあり、deny がなければ操作が許可されます。
3. マッチするポリシーがない場合は `undefined` となり、保護対象のランタイム操作では拒否として扱われます。

`security.strict_mode` が適用されるのは、アクターまたはスコープが欠けてコンテキストが不完全な場合だけです。ランタイム v0.3.32a は strict mode を有効にして起動します。レガシーまたは移行中のコードで、不完全なコンテキストを許容する動作を維持する必要がある場合にのみ無効にしてください。

```yaml
# .wippy.yaml
security:
  strict_mode: false
```

| コンテキスト | `strict_mode: false` | `strict_mode: true` |
|--------------|----------------------|---------------------|
| アクターとスコープが存在 | ポリシーを評価し、`allow` の場合のみ許可 | 同じ |
| アクターまたはスコープが欠落 | 保護対象の操作を許可 | 保護対象の操作を拒否 |

不完全なコンテキストを fail closed にする必要があるデプロイでは strict mode を有効に保ち、各サービスが必要なアクターとスコープを持って起動するようにしてください。strict mode を無効にしても、完全なスコープが返した `undefined` が allow に変わることはありません。

ポリシー構文、アクター、スコープ、トークンストアについては、[セキュリティリファレンス](../system/security.md)を参照してください。

## Lua の分離

各 Lua アクタープロセスは独自の Lua state を所有し、関数エントリは分離された state のプールを通じて実行されます。ランタイムは完全な Lua ホスト環境ではなく、制限された基本環境を開きます。

- アンビエントライブラリは、制限された `table`、`math`、`os`、`coroutine`、`string`、`errors` と、`channel`、`payload`、`print` などのコアグローバルです。
- `package.path` と `package.cpath` は空で、`package.loadlib` は無効です。
- レジストリに格納されたモジュールとライブラリは、`modules:` または `imports:` で宣言したチャンクからのみ参照できます。
- `require()` はそのスコープ内の集合を解決し、未宣言のレジストリモジュールに対して失敗します。

したがって、Lua コードにはホストのファイルシステム、ソケット、ネイティブプロセス、環境変数へ直接アクセスする API はありません。これらの機能には `fs`、`http_client`、`exec`、`env` などのランタイムモジュールを通じて到達し、その保護対象の操作では引き続きポリシーチェックが実行されます。

インポートしたライブラリのインポートが呼び出し元に漏れることはありません。各ライブラリとエントリポイントには独自のスコープ環境が与えられるため、ライブラリ内部で使用するケイパビリティが、そのライブラリをインポートした関数から自動的に利用可能になることはありません。

## WASM の分離

WASM コードは、設定されたホストインポートと WASI 設定を通じて動作します。環境値とファイルシステムマウントは WASM エントリで宣言する必要があります。インスタンス化の前に、ランタイムは設定された各環境エントリについて `env.get` を、各マウントについて `fs.get` を確認します。ファイルシステムマウントはホストルートを公開せず、設定されたファイルシステムをルートとして再配置されます。

WASM のソケットおよび外向き HTTP ホスト関数も、`socket.connect`、`socket.listen`、`socket.resolve`、`http_client.request` など、操作固有のチェックを実行します。

## ケイパビリティの取得と使用

多くのランタイムリソースはレジストリエントリです。モジュールはエントリ ID でリソースを取得し、対応するアクションを確認します。v0.3.32a の例を次に示します。

| 操作 | チェック | リソース |
|------|----------|----------|
| レジストリエントリを読む | `registry.get` | エントリ ID |
| 関数を呼び出す | `funcs.call` | 関数 ID |
| SQL データベースハンドルを取得 | `db.get` | データベースエントリ ID |
| ファイルシステムを取得 | `fs.get` | ファイルシステムエントリ ID |
| 環境値を読む | `env.get` | 変数名または ID |
| プロセスを生成 | `process.spawn` | プロセスエントリ ID |
| プロセスホストを選択 | `process.host` | ホストエントリ ID |

これらのチェックが行われる粒度はすべて同じではありません。たとえば `db.get` はデータベースハンドルの取得を認可します。そのハンドルを通じた個々の SQL クエリで `db.get` が再度チェックされることはありません。同様に、`fs.get` はファイル操作ごとに ABAC を適用するのではなく、ファイルシステムハンドルの取得を認可します。取得したハンドルの権限を保持させるべきでない信頼度の低いコンテキストには、そのハンドルを渡さないでください。

ネットワークモジュールは、ドキュメントに記載されている場合、各リクエスト、接続、リスナーについて追加のチェックを行います。操作で使用する正確なアクションとリソースは、該当するモジュールリファレンスを確認してください。

## コンテキストの継承

アクターとスコープは継承可能なフレームコンテキスト値です。関数呼び出しと生成されたプロセスは、呼び出し元が置換コンテキストを構築しない限り、これらを継承します。生成するプロセスにアクターまたはスコープを明示的に設定するには、該当する spawn 権限に加えて `process.security` 権限が必要です。

この継承により、認可は呼び出しチェーンに保持されます。一方で、権限の強い親は、信頼度の低いコードに処理を委譲するとき、意図的にコンテキストを狭める必要があります。

## レジストリの変更

エントリの読み取りとレジストリの変更には別の権限が必要です。標準の永続 changeset には `registry.apply` が必要です。v0.3.32a では、このチェックは空のリソースを使用し、エントリ単位または名前空間単位の書き込み判定ではありません。信頼できないエージェントに `registry.apply` を付与して、名前空間パターンで書き込みを制限できると想定しないでください。

プロセスローカルオーバーレイは、より限定された権限表層を持ちます。オーバーレイの所有者を確認し、影響を受けるエントリ ID に対して `registry.overlay.create.<kind>`、`registry.overlay.update.<kind>`、`registry.overlay.delete.<kind>` など操作固有のアクションをチェックします。[エントリレジストリ](../lua/core/registry.md)を参照してください。

## データ境界

テナント固有のデータベース、ファイルシステム、関数、環境変数には別々のレジストリ ID を使用し、意図した ID だけを許可するポリシーを作成してください。すべてのアクセス経路がチェック対象のランタイムモジュールを使用していれば、あるコンテキストが別テナントの保護対象リソースを取得することを防げます。

環境参照を使用すると、プロバイダーの資格情報をソースマニフェストから分離できます。プロバイダーは設定された `env.variable` を内部で解決できますが、それだけでアプリケーションコードから値を読めなくなるわけではありません。`env` をインポートし、同じ変数に対する `env.get` が許可されたコードは、その値を読み取れます。モジュールのスコープとポリシーの両方でシークレットを保護してください。

strict mode は、アクターまたはスコープが欠けた処理によるポリシー評価の迂回を防ぐため、マルチテナントデプロイで重要です。テナント ID を推測したりテナントポリシーを生成したりはしません。アプリケーションが正しいアクター、スコープ、リソース、ポリシー範囲を確立する必要があります。

## エージェントとツールの境界

Framework エージェントは、その定義と trait で選択されたツールをコンパイルします。ツールスキーマはツールに渡す引数を制約し、検証します。レジストリに格納されたツール実装は `funcs` 呼び出し経路を通じて実行されるため、対象の関数 ID に対して `funcs.call` がチェックされます。

ツール一覧とポリシースコープは相補的です。

- ツールを省略すると、通常のエージェントツールインターフェースからモデルがそのツールを選べなくなります。
- `funcs.call` を拒否すると、コンパイル済み一覧にツールが含まれていても実行できません。
- `funcs.call` を許可しても、未宣言のツールがモデルの一覧に追加されることはありません。

ツールラッパーと外部統合も追加のアプリケーションコードとして扱ってください。これらはランタイムチェックの代わりにはならず、それぞれのネットワーク資格情報と認可規則もレビューする必要があります。

## デプロイ側の責務

Wippy の実行およびポリシー境界は、インフラストラクチャ制御の代わりにはなりません。

- ストレージの暗号化とバックアップポリシーは、設定したデータベース、ディスク、オブジェクトストアが担います。
- VPC、ファイアウォール、サービスポリシーがネットワークレベルの到達性を制御します。
- Wippy の認可を適用する前に、認証によってユーザーまたはサービスの ID を確立します。
- ホスト管理、SSH アクセス、データベース管理者の操作には、インフラストラクチャの監査ログが必要です。
- テナントごとの CPU とメモリのクォータには、デプロイレベルのリソース制御が必要です。

OpenTelemetry は設定されたランタイムおよび Framework の操作をトレースできますが、トレース範囲は有効な計装によって異なります。[可観測性](../guides/observability.md)を参照してください。

## レビューチェックリスト

- 不完全なコンテキストを fail closed にする必要がある場所では、`security.strict_mode` を有効に保つ。
- 各サービスに意図したアクターとスコープを与える。
- 宣言された Lua モジュール／インポートと、その保護対象操作に対応するポリシーの両方をレビューする。
- 永続レジストリ全体の変更を意図しない限り、信頼できないコードに `registry.apply` を与えない。
- 取得したデータベースまたはファイルシステムのハンドルを信頼境界を越えて共有しない。
- テナントのリソースをレジストリ ID で分離し、各テナントのスコープ外で拒否されることをテストする。
- インポートのスコープと `env.get` ポリシーの両方で環境シークレットを保護する。
- ランタイム認可とは独立して、トレースとインフラストラクチャ制御を検証する。
