# Wippy가 Lua를 사용하는 이유

Wippy는 프로세스 격리와 임베딩 요구사항에 잘 맞기 때문에 Lua를 주 런타임 언어로 사용합니다. 이 페이지는 그 설계 선택과 절충점을 설명하며, 프로그래밍 언어의 일반적인 우열을 매기지 않습니다.

이 문서는 실행 가능한 튜토리얼이 아니라 개념 설계 노트입니다. 런타임 속성을 설명하고 구체적인 API를 정의하는 참조 문서로 안내합니다.

## 런타임 요구사항

Wippy는 사용자 정의 로직을 격리된 프로세스에서 실행합니다. 각 프로세스는 자체 메모리를 가지며 런타임이 노출한 기능만 전달받습니다. 많은 프로세스가 동시에 실행될 수 있으므로 임베디드 언어는 다음 조건을 충족해야 합니다.

- **낮은 프로세스별 오버헤드.** 프로세스 수가 늘어도 메모리 사용량이 실용적인 수준이어야 합니다.
- **기능 격리.** 런타임이 각 프로세스에서 사용할 수 있는 모듈, 함수, 시스템 작업을 제어해야 합니다.
- **프로세스 내 임베딩.** Wippy의 Go 코어가 각 프로세스의 언어 환경을 생성하고 설정하고 중지할 수 있어야 합니다.
- **제어된 모듈 로딩.** 모듈은 임의의 파일 시스템 경로가 아니라 런타임 허용 목록 또는 선언된 레지스트리 import에서 와야 합니다.
- **작은 언어 표면.** 애플리케이션 코드는 읽기 쉽고 생성, 검토, lint하기 쉬워야 합니다.

## 검토한 대안

### Python

Python은 대규모 애플리케이션 및 데이터 생태계를 제공하지만 인터프리터, import 모델, 패키지 전제가 Wippy의 프로세스별 임베딩 및 기능 모델과 맞지 않습니다. Python 서비스는 명시적인 서비스 경계를 통해 Wippy와 통합할 수 있습니다.

### JavaScript

JavaScript 런타임에는 여러 임베딩 옵션이 있습니다. 하지만 모듈 및 패키지 생태계에는 Wippy가 사용하는 레지스트리 범위 로딩 모델을 제공하기 위한 별도의 통합 계층이 필요합니다. Wippy는 애플리케이션 코드에 더 작고 호스트가 제어하는 Lua 런타임 표면을 선택했습니다.

### Go

Go는 Wippy 코어 런타임에 사용됩니다. 컴파일된 Go 코드와 플러그인은 사용자 정의 애플리케이션 로직에 필요한 격리된 프로세스별 임베디드 환경을 제공하지 않습니다.

### WebAssembly

WebAssembly는 Lua를 주 작성 언어로 대체하는 대신 상호 보완적인 역할을 합니다. 역할 분담은 [Lua와 WebAssembly](#lua와-webassembly)에 설명되어 있습니다.

## Lua가 적합한 이유

### 호스트 제어 임베딩

Lua는 호스트 애플리케이션 내부에서 실행되도록 설계되었습니다. Wippy는 각 프로세스의 환경을 만들고 스케줄러와 레지스트리에 연결하며 전역 값과 모듈 로더를 제어합니다. `require`는 해당 환경에 이미 설치된 모듈만 읽습니다. 여기에는 항상 사용 가능한 기본 모듈과 표준 라이브러리, 실행 가능 엔트리의 ambient `process` 모듈, `modules:`에서 허용한 내장 런타임 모듈, `imports:`로 선언한 레지스트리 라이브러리가 포함됩니다. 파일 시스템 경로를 검색하거나 네트워크에서 패키지를 설치하지 않습니다. 따라서 애플리케이션 수준 로딩 규칙 없이 엔트리마다 서로 다른 모듈 집합을 제공할 수 있습니다.

### 언어 표면

Lua는 간결한 구문과 작은 표준 환경을 제공합니다. Wippy는 타입 annotation과 lint를 추가하여 기본 실행 모델을 바꾸지 않고 코드를 점진적으로 검사할 수 있게 합니다.

### 협력적 스케줄링

Lua coroutine은 Wippy의 협력적 스케줄링 모델에 대응합니다. 프로세스가 channel 또는 I/O 작업 중 yield하면 스케줄러가 다른 작업을 실행할 수 있습니다.

## 절충점

Lua에는 pip나 npm에 견줄 만한 프로세스 내 패키지 생태계가 없습니다. Wippy는 네트워크에서 패키지를 설치하는 대신 허용 목록을 통해 내장 런타임 모듈을 제공하고 레지스트리 import를 통해 애플리케이션 라이브러리를 제공합니다. 대규모 외부 라이브러리에 의존하는 워크로드는 서비스 또는 WebAssembly 컴포넌트로 실행할 수 있습니다.

다른 언어에 익숙한 개발자에게 Lua가 낯설 수도 있습니다. 구문은 간결하지만 프로덕션 코드에는 여전히 팀 규칙, 검토, lint가 필요합니다.

## Lua와 WebAssembly

Wippy는 상호 보완적인 두 런타임을 제공합니다.

- **Lua**는 애플리케이션 로직, 도구, agent의 주 런타임입니다.
- **WebAssembly**는 컴파일된 워크로드와 WASM을 대상으로 빌드할 수 있는 기존 코드를 실행합니다.

Lua 및 WASM 프로세스 엔트리는 Wippy 프로세스 모델을 사용하며, Lua 및 WASM 함수는 등록된 함수 엔트리로 노출됩니다. 두 통합 모두 레지스트리와 런타임 보안 정책을 통해 설정됩니다. Lua 코드는 등록된 WASM 함수를 호출할 수 있고 WASM 프로세스는 등록된 Lua 함수를 호출할 수 있습니다.
